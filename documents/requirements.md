# Forge 需求

Forge 将 EROS 软件及其依赖，在受控构建环境中转换为可消费、可交付、可追溯的制品。Bazel 管理构建图，CMake 负责包内构建，Conan 负责第三方依赖。

本文规定必须满足的行为与责任边界；[技术设计](technical-design.md)解释实现机制，[验收设计](test-design.md)规定判定方法。接口说明和构建成功不能代替验收证据。

## 1 核心契约

1. 源码、锁定依赖、工具环境与有效配置共同决定制品。实际读取的输入必须声明。
2. 执行平台与目标平台分离。编译器、目标头文件、链接库、加载器和部署运行库必须符合目标 ABI。
3. 库消费者仅通过一个 `deps` 获得必要的编译、链接和运行信息。
4. 缓存结果必须完整、可迁移，不依赖生产机器的临时目录或用户 Conan 缓存。
5. 发布程序、运行依赖、资源和匹配符号可以独立收集，交给目标环境执行与分析。
6. 受支持构建全流程在官方构建容器内执行。外层入口仅管理环境，构建图、目标和配置仍由 Bazel 管理。

## 2 参与者

| 角色 | 责任 |
| --- | --- |
| Forge 维护者 | 统一构建入口、平台预设、工具校验、规则、配置归一化、导出接口、运行闭包和打包 |
| 环境与 SDK 维护者 | 按执行架构发布固定的官方构建镜像及环境清单，维护编译工具、目标头文件与库，保证编译和部署的 ABI 一致 |
| 包维护者 | 包内构建、依赖锁、公共接口、插件和资源声明、跨包兼容性 |
| 包消费者 | 通过 `deps` 使用库，通过 `data` 声明额外运行文件 |
| CI 维护者 | 使用与开发一致的官方构建环境，维护缓存服务、目标环境、运行测试、制品与符号归档、core 关联 |

## 3 技术决策

| 编号 | 决策 | 约束 |
| --- | --- | --- |
| D00 | 平台预设表达完整构建场景 | 内部分离 execution 与 target，不向普通构建开放任意 host、target、glibc 组合 |
| D01 | 开发和 CI 使用固定的官方构建镜像 | 所有受支持构建在官方 OCI 镜像内进行，以 Docker 为标准运行时；按执行架构锁定镜像摘要，环境可校验，升级须显式评审 |
| D02 | 编译与部署使用同一固定 SDK 的目标 glibc | 头文件、链接库、加载器和运行库必须匹配；解释器路径或 RPATH 不构成 ABI 一致性证明 |
| D03 | 支持开发者与 CI 共享远程缓存 | 相同受控输入可在独立机器复用，不访问生产机器的私有目录 |
| D04 | 缺少匹配 Conan 二进制时自动源码构建 | 使用锁定配方与目标变体；失败不得通过换版本或降低要求绕过 |
| D05 | 普通构建必须消费锁定依赖 | 允许下载和缺包构建，不允许隐式更新锁；更新结果需评审并纳入版本控制 |
| D06 | 支持单架构构建和单命令多架构构建 | 每个分支有真实配置和 payload，能力限于执行机具备的工具链集合 |
| D07 | Bazel 主导包间依赖，CMake/Conan 管理包内构建 | 不要求把完整 Conan 图公开映射为 Bazel 目标 |
| D08 | 原生 Bazel 目标直接消费 CMake/Conan 库 | 导出编译与链接接口，不只是提供文件下载 |
| D09 | 消费者只声明一个导出依赖 | 提供方传递公开头文件、defines、静态/PIC/动态形式及必要传递链接项 |
| D10 | Conan 库优先静态，必要动态依赖随包交付 | SDK 基础运行库与包私有库具有明确边界 |
| D11 | 各 deb 携带自己的私有动态依赖 | 安装路径不冲突，加载路径明确，不强制建设统一第三方依赖 deb |
| D12 | 第三方版本按 Bazel 包独立锁定 | 不同包可使用不同版本；同进程 ABI、符号互置和插件兼容性由维护者负责 |
| D13 | 使用 `separate_debug_info` 控制独立符号交付 | Release 默认启用；保持优化模式，CI 保存匹配符号 |
| D14 | 符号覆盖原生、CMake 和 Conan 第三方代码 | 无可用匹配符号的二进制须重建或失败，不以警告替代要求 |
| D15 | Sanitizer 覆盖业务代码和 Conan 依赖 | 插桩编译与链接参数参与二进制选择和缓存隔离 |
| D16 | 缓存未命中时在本机构建容器内执行 | 不要求远程执行服务；禁止远程执行不能同时禁止所需的远程缓存 |
| D17 | CI 负责目标执行 | Forge 导出测试程序和依赖，CI 准备设备/模拟器、运行并保存结果 |
| D18 | GCC 支持 ASan、UBSan、TSan，不支持 MSan | MSan 请求须在配置阶段明确拒绝，不切换到其他编译器伪装支持 |
| D19 | 支持 ASan+UBSan | 两种请求顺序语义一致；ASan+TSan、TSan+UBSan 和未确认组合不得静默覆盖 |
| D20 | 插件与资源显式声明 | `data`、安装映射或 `exports.runtime_files` 形成运行根；插件自身的依赖也需交付 |
| D21 | 提供透明的 Bazel 入口与交互开发环境 | 宿主入口为可执行程序，不要求 `source`；容器内可直接使用 `bazel`；两种入口使用同一镜像配置，不另设业务构建参数或将 Docker 调用写入 Bazel 规则 |

### 3.1 构建环境与入口

1. 环境维护者发布可直接获取的构建镜像，而不只提供 Dockerfile。镜像构建配方及工具、SDK 来源须固定；镜像摘要与执行架构映射纳入版本控制，不以 `latest` 或可覆盖标签决定实际环境，普通构建不隐式升级或重建镜像。
2. Bazel 客户端、服务端、工具发现、repository rule 和构建 action 均在容器内执行。宿主不必安装项目构建工具或 SDK；不得借用宿主系统工具目录或用户 Conan 工作缓存补齐依赖。镜像缺失且无法获取、校验失败或容器无法启动时明确失败，不静默回退裸机。
3. 宿主入口接受标准 Bazel 启动选项、子命令和参数，至少覆盖 `build`、`test`、`run`、`query`；保持参数边界、标准输入输出、交互终端、信号和退出码语义。进入交互开发环境后直接调用 `bazel`，与宿主入口具有等价的有效配置与构建结果；`bazel run` 默认在容器内运行程序。
4. 入口统一工作目录、挂载、必要环境变量和用户权限，支持连续调用复用 Bazel 服务端及磁盘缓存，不因每次调用入口而强制销毁服务端。不同工作区、环境版本及并发实例的构建状态不得互相污染，生成文件应可由调用者正常管理。
5. 构建记录包含实际使用的平台镜像摘要、工具环境及 SDK 身份。影响构建语义的工具、SDK 和环境差异必须通过声明输入参与相关缓存身份；不能假定外层镜像摘要自动进入 Bazel action key，也不能以容器替代实际输入声明和环境校验。容器内实际采用的 Bazel 沙箱策略须明确并验证，不因使用容器而直接关闭沙箱。

发布环境基线与实际平台镜像摘要关联。运行时重新采集工具身份不能替代已发布基线；环境意外变化必须被拒绝，只有评审过的环境升级才能更新基线。入口保留调用工作区的目标与 rc 解析，适用于 Forge 本身及消费模块，不将调用强制切换到 Forge 根目录。

## 4 平台与变体

| 预设 | 执行 CPU | 目标 CPU | 用途 |
| --- | --- | --- | --- |
| `linux_x86_64` | x86_64 | x86_64 | 原生构建 |
| `linux_arm64` | ARM64 | ARM64 | 原生构建 |
| `linux_x86_64_cross_arm64` | x86_64 | ARM64 | ARM64 交叉编译与部署配置 |
| `linux_arm64_cross_arm64` | ARM64 | ARM64 | ARM64 交叉部署配置，不等同于原生 ABI |

原生自动选择仅适用于受支持的执行环境。安装了某个目标的编译器，不表示可以忽略预设的执行 CPU 约束。ARM64 执行机不承诺交叉构建 x86_64。

官方镜像按执行 CPU 提供对应环境，锁定具体平台镜像摘要；同一多架构标签不表示环境身份相同。容器不改变预设的执行 CPU 约束，也不自动提供目标程序执行能力。

有效变体包含环境/SDK 身份、平台、编译器及 C++ ABI、Debug/Release、sanitizer、PIC/链接策略和调试要求。Conan 的 `host` 对应目标库，`build` 对应运行构建工具的机器；两者不能混用。

SDK 不具备时，编译和 ELF 检查只能形成构建层证据。发布到目标运行环境前，仍必须满足 D02；不得将这种构建标记为目标 ABI 或运行验收通过。

## 5 功能需求

| 编号 | 需求 | 验收要求 | 决策依据 |
| --- | --- | --- | --- |
| FR-01 | 固定环境与 SDK | 校验实际工具和 SDK 内容符合已发布环境身份，目标头文件、链接库、glibc 与加载器一致；不匹配时失败 | D00-D02 |
| FR-02 | 平台预设 | 正确选择执行工具链、目标 CPU 与 ABI，拒绝不支持的预设组合 | D00-D01 |
| FR-03 | 包级锁定 | 锁定传递引用和配方修订；普通构建不改锁；显式更新不影响其他包 | D05、D12 |
| FR-04 | Conan 获取与构建 | 获取匹配二进制，缺失时按锁构建；SDK、插桩、模式和符号不静默降级 | D04、D14-D15 |
| FR-05 | 单目标 C++ 接口 | 消费者仅用 `deps` 完成编译、传递链接和运行；支持可执行文件及共享库消费者 | D07-D09 |
| FR-06 | 静态优先与动态闭包 | 必要非 SDK 动态库、传递依赖和 SONAME 关系完整 | D10 |
| FR-07 | deb 私有依赖 | 不同包/版本安装不覆盖，移除一个不破坏另一个 | D11-D12 |
| FR-08 | 共享缓存与本地执行 | 相同受控输入跨机器可复用，输入变化正确失效，未命中本地执行 | D03、D16 |
| FR-09 | 单架构和多架构 | 分支真实构建，ELF 架构与 deb 元数据一致 | D06 |
| FR-10 | 模式一致性 | 三条构建路径的模式和附加特性一致，切换配置不依赖清空缓存 | D01、D04、D13-D15 |
| FR-11 | 调试制品 | 匹配业务和第三方函数/源码的符号作为显式输出收集 | D13-D14 |
| FR-12 | Sanitizer | 业务和依赖实际插桩，支持规定集合，拒绝 MSan 与互斥组合 | D15、D18-D19 |
| FR-13 | 插件与资源 | 显式运行根及其依赖同时进入运行布局与交付布局；缺项/冲突失败 | D20 |
| FR-14 | 测试导出 | 输出完整测试闭包、配置和执行说明，导出不要求运行交叉程序 | D17、D20 |
| FR-15 | 输出真实性 | 缺少声明的程序、库或头文件必须失败；库目标不需要伪程序 | D08、D10 |
| FR-16 | deb 元数据 | 已知 CPU 正确映射，未知 CPU 失败，`all` 显式声明，版本输入变化有效 | D06、D11 |
| FR-17 | 制品追踪 | 关联源码、锁、配置、实际平台镜像摘要、工具环境、SDK、二进制、运行闭包和匹配符号 | D01-D02、D05、D13-D14 |
| FR-18 | 完整输入 | `.cmake`、脚本、模板、头文件、配方附属文件等变化触发对应重建 | D03、D05、D08 |
| FR-19 | 官方构建环境交付 | 独立干净宿主无需预装项目构建工具，按锁定摘要获取匹配执行 CPU 的镜像；开发与 CI 使用相同环境身份，环境不可用时不回退裸机，语义相关环境升级正确失效缓存 | D00-D03、D16 |
| FR-20 | 统一构建入口 | 宿主入口与容器内直接调用对相同参数产生等价配置和结果；验证标准子命令、启动选项、含空格参数、标准流、交互终端、信号、失败退出码及容器内 `run` 行为 | D01、D21 |

## 6 质量要求

| 编号 | 要求 | 判定 |
| --- | --- | --- |
| NFR-01 | 可复现语义与可信缓存 | 同一声明输入具有相同构建语义，配置/SDK 变化不能错误复用；不承诺任意第三方构建天然逐字节一致 |
| NFR-02 | 隔离与迁移 | 不写回源码、不污染用户 Conan 缓存，配置间互不覆盖；快照和制品能脱离生产目录使用 |
| NFR-03 | 诊断与资源控制 | 错误包含目标、配置和阶段；内部并行度有预算，检查有时间界限，输出目录与 inode 使用有管理策略 |
| NFR-04 | 开发体验与状态复用 | 连续调用可复用 Bazel 服务端和磁盘缓存；工作区、环境版本及并发状态隔离，调用者可管理生成文件；无需学习独立的业务构建参数 |

## 7 范围与发布准入

不要求任意宿主兼容、用户自由选择 glibc、全局统一第三方版本、完整 Conan 图公开化、远程执行服务、设备调度器或 MSan/Clang 工具链。

官方容器要求适用于原生 Bazel、CMake 和 CMake/Conan 全部受支持构建路径，包括开发、CI、验收和发布构建。裸机构建仅作为显式选择的非标准排障或工具链实验模式，不承诺与标准构建等价，不得读写正式共享缓存或用于发布。

官方镜像统一用户态，不承诺任意宿主内核、CPU 或容器安全策略下行为相同；须声明支持的宿主与运行时条件，不要求额外容器运行时兼容。构建容器内运行不替代干净目标环境或设备上的运行验收，也不降低 D02 的 SDK/ABI 一致性要求。

包维护者必须声明公共接口和运行文件；环境维护者必须提供可核验的 SDK 与运行库关系。源码固定使用带摘要的归档或固定提交及子模块，不在普通构建中追踪浮动分支。

通过[测试设计的需求追踪表](test-design.md#traceability)验收。需求变更同步更新决策、FR、设计和测试。依赖升级只更新所属包的锁定输入和相关接口。未运行、受阻或只有 ELF 检查的范围不能计为运行通过。

当前本机 Linux/amd64 镜像已构建并按 `docker/image.lock.json` 中的本地镜像 ID 锁定；根目录 `./forge-bazel`、`./forge-shell` 提供持久容器中的 Bazel 与交互入口。示例 01–04 的 Debug/Release 共八次原生运行，以及现有 TC-ENV-01/local、TC-ENV-02/local、TC-DEP-05/local 已在该环境通过。此为本地构建交付，不等于 D01、FR-19 的官方可获取多架构镜像或 FR-20 的全部入口行为已验收：没有 registry 发布、ARM64 原生宿主、匹配目标 SDK、目标设备或完整 CI/跨机缓存证据。新增环境/入口 TC 尚未全部接入 runner；未验证行为不能标为 PASS。完整目标 SDK 的交付范围仍待确认，D02 和发布准入要求保持不变。
